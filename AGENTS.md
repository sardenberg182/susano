# AGENTS: repositório susano (o modelo, não um projeto)

Este repositório é a fonte do Susano: um template Copier (`modelo/`), um plugin do Claude Code (`plugin/`) e um pacote de chat (`dist/chat/`, gerado, fora do Git), todos da mesma fonte, `modelo/00_susano/`. Quem abre este repositório com um agente está mantendo o modelo, não usando o Susano num projeto: para isso, veja o `README.md`.

- Dono: Matheus Sardenberg (Sarden). O Raijin propõe mudanças; o Sarden aprova. Nenhum merge sem o OK dele.
- Fonte única: conteúdo do método só em `modelo/00_susano/`. `modelo/00_susano/INDICE.md`, `ATIVOS.md`, `MANIFEST.sha256`, `modelo/.claude/skills/susano-*/`, `plugin/` e `dist/` são gerados; nunca edite à mão.
- Regenerar depois de qualquer mudança em `modelo/`: `python3 modelo/scripts/brain.py --raiz modelo indice`, `skills`, `manifesto`; depois `python3 ferramentas/construir_plugin.py`.
- Testar antes de propor (o mesmo que o CI roda): `python3 modelo/scripts/brain.py --raiz . varrer --perfil publico`, `bash testes/testar_geradores.sh` (árvore limpa), `bash testes/testar_modelo.sh` (projeto padrão e com nomes longos: validate, susano-check, migrar e os casos de `testar_camada.py`), `bash testes/testar_atualizacao.sh` (v0.3.0 para a candidata), `bash testes/testar_plugin.sh` e `bash testes/testar_pacote_chat.sh`. Teste mecânico, avaliação com modelo (`testes/rodar_casos.py`, variantes plugin e template) e teste de instalação real (chat, pelo `LEIA-ME.md` do pacote) são coisas diferentes: o registro diz qual rodou.
- Versão: linha nova no topo do `CHANGELOG.md` (a versão do plugin é lida dali), `README.md` com a tag nova. Antes do merge, o `CHANGELOG.md` registra a autorização do Sarden para distribuir (data, hora, canal e as palavras dele): agente e dono usam a mesma conta no GitHub, então a aprovação do PR não serve de registro. Tag `vX.Y.Z` só depois dos testes e do registro.
- Autoria pública dos commits: o agente assina `Raijin <raijin@example.com>`; o Sarden usa o noreply da conta do GitHub (Settings → Emails → Keep my email addresses private), o que vale também para os merges feitos pela web ou pela API: merge e rebase do GitHub gravam a conta de quem integra, com o e-mail dela naquela hora, então o e-mail privado vem antes de qualquer merge. O CI confere os commits de cada PR e, no push da `main`, tudo o que entrou, inclusive os commits de merge e os refeitos pelo rebase (`ferramentas/conferir_autoria.py`). Reescrever histórico é decisão do Sarden, nunca do agente.
- Convenções do conteúdo: PT-BR com termos técnicos em inglês; corpo de skill, agente e estilo em inglês; nenhum travessão em arquivo nenhum (`grep -rn` do caractere U+2014); marcadores [DADO], [INFERÊNCIA], [VERIFICAR], [LACUNA], [CONTRADIÇÃO], [SENSÍVEL]; todo fato de produto com data.
- Privacidade: nenhum dado de cliente, nome ligado à operação do Sarden, e-mail, telefone, credencial ou ID real entra aqui. O nome civil do Sarden aparece só em copyright, `sobre_o_sarden.md` e autoria do plugin. A Oficina (persona) é outro repositório e nunca entra neste. O CI inspeciona todo arquivo no perfil público; exceção só de contato ou binário, por arquivo exato e com motivo, em `PRIVACIDADE_EXCECOES.md`; segredo, cartão e CPF de teste são montados em tempo de execução.
- Textos aprovados pelo Sarden (`identidade.md` v0.1.6, `sobre_o_sarden.md`, os 8 DNAs, a licença) só mudam com nova aprovação dele, registrada no frontmatter `aprovado:`. Texto em `revisao_pendente` muda com registro no CHANGELOG; `python3 modelo/scripts/brain.py --raiz modelo audit` mostra o inventário da revisão editorial.
